# ADR 0025 — Release 0.1.0: the `@tenonkit` scope, `create-tenon`, agent files

- Status: proposed
- Motivation: the user wants to publish version 0.1.0. An app built from npm must be as easy for an agent as the
  apps in this repo, for Claude Code and for agents that read `AGENTS.md` (Codex, Cursor, Copilot and others).

## Facts
- **Scope:** `@tenon` and `@tenonjs` cannot be used. The user created the npm organisation **`tenonkit`**
  (owner `olevator`).
- **Names already taken or free:** the unscoped packages `tenon`, `tenon-cli` and `usetenon` belong to others;
  `create-tenon` is free.
- **Nothing is published yet.** All 17 framework packages are `0.0.0`, with `files` and an MIT licence field; the
  repository has no `LICENSE` file. Examples and benchmarks are `private`.
- **The skill points into this repository:** `examples/bookmarks`, `examples/cart/edge.ts`, `examples/blog`. An
  app installed from npm has none of these paths.
- **npm publishing needs 2FA:** tokens that bypass 2FA can no longer publish. Publishing is manual, with the user's
  one-time code.

## Decision 1 — Scope `@tenonkit`, name Tenon
- **Rename:** every package moves from `@tenon/x` to `@tenonkit/x`, together with every import, test, example,
  the skill, `CLAUDE.md` and the JSON Schema ids. The framework keeps its name, **Tenon**.
- **CLI binary:** stays `tenon`. Docs keep `pnpm exec tenon`, so the unscoped `tenon` package of someone else is
  never run.
- **Old ADRs:** keep `@tenon/…`, because they are history. This ADR records the rename.

## Decision 2 — `create-tenon`
**Usage:** `npm create tenon@latest my-app` (or `pnpm create tenon my-app`). It creates a blank, working app of the
shape trial 0007 used:
- `tenon.config.ts` with one static page;
- `routes.ts`, `server.ts`, `serve.ts`, `app.css`, `package.json` (dependencies `^0.1.0`) and `tsconfig.json`.

It checks that the app validates and builds, as the trial scaffolds did.

**The agent is chosen at creation:**

| Choice | Files |
|---|---|
| `claude` | `CLAUDE.md` + `.claude/skills/tenon/` (loaded by Claude Code as the `tenon` skill) |
| `agents` | `AGENTS.md` + `.agents/skills/tenon/`. `AGENTS.md` says to read `.agents/skills/tenon/SKILL.md` before writing Tenon code, because not every agent loads skill folders by itself |
| `both` | both sets, with the same skill content |

- **Interactive** when run in a terminal. **`--agent claude|agents|both`** skips the question, because an agent that
  runs `create-tenon` cannot answer prompts.
- **The two agent files have the same body:** checks, rules and where the reference is. Only the skill path
  differs.
- **Dependencies:** none (`node:readline`, `node:fs`). Node ≥ 22.18 is checked first, with a clear message,
  because type stripping is required.

## Decision 3 — The skill ships with the CLI and is updated by `tenon skill`
- **Where the skill ships:** `@tenonkit/cli` includes the skill files. `create-tenon` copies them from there,
  and **`tenon skill [--agent claude|agents|both]`** rewrites them after an upgrade. This keeps the skill at the
  installed framework version.
- **One source:** `.claude/skills/tenon/` in this repository stays the only source. A build step copies it into the
  CLI package, and a test fails if the copy is stale (like `pnpm schema`).
- **Paths inside the published skill:**
  - the reference app `examples/bookmarks` (about 15 KB) ships inside the skill as `example/`;
  - repository paths become skill-relative (`example/features/bookmarks/model.ts`);
  - the patterns name their API instead of a repository example they are "used in";
  - `examples/cart/edge.ts` becomes an inline snippet in `reference.md`.

  `examples/bookmarks` stays the source of `example/`, so its gate checks keep covering what agents copy.
- **This repository's own agent files:** `AGENTS.md` is generated from `CLAUDE.md` by `pnpm agents`, with a
  staleness test, instead of the untracked hand copy. The hand copy is already stale, and its paths say
  `.Codex/skills`.

## Decision 4 — Release procedure (no CI, per the cost rules)
**Metadata, set on every package:**
- version `0.1.0`;
- `repository`, `homepage`, `bugs`;
- `engines: { node: '>=22.18' }`;
- `publishConfig: { access: 'public' }`;
- a short `README.md`;
- a root `LICENSE` (MIT) that ships in every package;
- a `CHANGELOG.md` whose 0.1.0 entry summarises Phases 1–9 and ADRs 0022–0024.

**Rehearsal with the real artefacts before publishing:**
1. `pnpm -r pack` gives the tarballs exactly as they would be uploaded (pnpm replaces `workspace:*` with `0.1.0`).
2. In a new temporary directory outside the workspace, run the packed `create-tenon` with `--agent both`, and
   install the packed tarballs in place of the registry.
3. In that app, run `tsc`, `tenon validate`, `tenon build` and `tenon skill`. Start the server and request the
   page, then run `tenon plan`.
4. The rehearsal fails on:
   - any file missing from a tarball;
   - an import that does not resolve;
   - a skill path that does not exist in the created app.

**Publish:**
- `pnpm -r publish --access public --otp <code>`, run only after the user confirms and gives the code; or the
  user runs it.
- Then a `v0.1.0` git tag and a push.

## What the user decides (open)
- The copyright holder written in `LICENSE`.
- Whether `github.com/olevatorr/Tenon` becomes public at release (npm pages link to it).

## Verification
- The gate is green after the rename. Parity stays 24/24, lock files stay valid, and the IR does not change: the
  scope name does not appear in the IR.
- New tests:
  - `create-tenon`: each `--agent` choice creates the expected files, and a non-empty directory is refused;
  - `tenon skill`: rewrites stale files;
  - the staleness tests for the skill copy and `AGENTS.md`.
- The rehearsal above passes.
