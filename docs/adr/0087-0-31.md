# ADR 0087 — 0.31: what trial 0028 met

- **Status:** accepted (owner, 2026-10-13: "可以繼續做測試了，直接做到完不用問我意見").
- **Evidence:** trial 0028 (ADR 0086, `docs/trials/0028-regression-round.md`):
  - R1, a new app built on 0.30.1 by an agent that never saw the earlier fixes;
  - R2, trial 0023 change 9 run twice more on 0.30.1.
  Each item was reproduced before it was judged, most of them on a copy of R1's app.
- **No API change.** `hozu migrate` 0.30 → 0.31 rewrites nothing.

## Accepted
| # | Found | Decision |
|---|---|---|
| A1 | R2: one run of two failed because the remove dialog flashed past while a Done task was removed, and nothing told the agent | `hozu browse` names what a step showed and removed before it settled. Under the step it prints `shown briefly: "Remove “Ship…”? …" for 15 ms`; `--json` puts it in `brief`. A MutationObserver started with the step records elements with text that were added and then removed. Moves and kept elements are not counted, and the line is not a difference between the JavaScript modes. The testing topic says what such a line usually means: a view shows content in a state the change now passes through |
| A2 | R1: `hozu browse` uploaded a 0-byte file | The browser protocol leaves File and Blob bytes out of an intercepted request, so the in-process handler got an empty file. Browse adds a script to every page: a `fetch` whose body holds a File or Blob is sent as its bytes, with the same multipart content type |
| A3 | R1: HZ079 told the agent to remove a caller class that HZ072 told it to mark with `!` | When a component's variant and a caller's class set one property on a component's root, HZ072 alone reports it. HZ079 skips a pair where one class is the caller's and the other the component's |
| A4 | R1: HZ026 said the typography plugin's `lead` produces no CSS | The plugin matches it as `[class~="lead"]`. `selectorClasses` reads that form too |
| A5 | Found while checking A4 | The styles cache in `node_modules/.cache/hozu` is keyed by the CLI version too, so upgrading Hozu recompiles instead of reusing the old answer |
| A6 | R1: `hozu add kit` asked for `@hozu/css` that was installed | The error names only the missing packages |
| A7 | R1: `in "<text>"` did not match a `nav`; `--help` did not list `upload` | `in` also scopes to `nav`, `section` and dialogs; `--help` lists `upload` |
| A8 | R1: guide gaps | The auth topic says, in its short form, that a 403 page still renders its views and how to gate them. It also says to clear a password from context, and types the shared `part()` for `access: { allow }`. The volume line of the JSON-file recipe and a stale example reference are fixed |

## From the review before the tag
- `brief` counted an element added and removed in one task, which was never painted: an element now has to stay
  across an animation frame. A child removed before its parent is folded into the parent, and pending records are
  read rather than dropped.
- `FILE_BODIES` covers `fetch(url, { body })`, which the Hozu client uses. A body passed as `new Request(url, { body })`
  without `init`, and XHR uploads, still arrive without their file bytes.
- The auth example's key is `Forbidden` (the refusal of `access`); a declared error has its own key. The shared
  `part()` is typed with an inline session type.

## Declined or recorded
| Item | Why |
|---|---|
| A 403 page that renders no views | The status comes from `head.failed`, and the body stays the page's views, so a page can explain itself ("Task not found", "Admins only") through the same query. Data stays protected by `access`. A8 documents it |
| HZ078 right after `hozu add component` (R1) | Not reproduced on a fresh app; R1's `--sync` cleared it |
| R1 putting the password in context | Context is the way into a mutation. A8 covers clearing it |
