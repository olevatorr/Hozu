# ADR 0050 — 0.12: large apps and many servers, `hozu call` and the DevTools API panel

- **Status:** accepted (owner, 2026-10-03): D1–D7 as recommended; one release, not split.
- **Scope:** what ADR 0049 moved out of 0.11:
  - the five scale items from the scale analysis;
  - `hozu call`;
  - the DevTools API panel;
  - `runs` in `inspect` / `impact` / `explain` and DevTools Layers.
- **Problem:** per request and in the browser, Hozu stays fast as an app grows. The infrastructure for a large
  deployment and a large codebase is missing:
  1. **Unbounded memory.**
     - The data cache (`packages/data/src/runtime.ts`) is a `Map` with a tag index and no eviction.
     - The page cache `memoryCache()` (`runtime-server/src/cache.ts`) is an unbounded `Map`, and `deleteTags` scans
       every page.
     - Many public keys (a million `/products/:id`, free-text search) grow memory without limit.
     - `PageCache` is replaceable; the data cache is not.
  2. **No cross-process invalidation.**
     - Tag invalidation (`dropPages`, `data.invalidate`) and the live listeners (`broadcast` over `/_hozu/live`)
       live in one process.
     - With four instances, a mutation on A leaves B–D serving stale data until their TTL. A `'static'` public
       query on B–D never refreshes, and live pushes reach only A's clients.
  3. **One `fns.js` for the whole app.**
     - `fnsModule(build)` ships every `fn` of every feature to every page with an island.
     - Each `fn` repeats the module helpers it uses.
     - It grows linearly with the app, even though the IR knows which page needs which `fn`.
  4. **Every check is a full run.**
     - `hozu check` runs a full `tsc --noEmit`, every rule and every contract on every call.
     - Small apps are fast (`examples/cart` 0.4–1.0 s, `site` 0.8 s, measured 2026-10-03), but per-tag attribute
       types are heavy (cart: 52.9k instantiations, budget 65k).
     - An agent runs check after every change, so the cost multiplies. Trial 0021 measured a slightly positive
       per-step cost slope against Nuxt over steps 13–28 (target ≤ 0).
  5. **Many islands.**
     - Every island carries its node JSON.
     - Benchmark 0001: 100 buttons give 18.6 KB of HTML against about 12.6 KB for the other frameworks. It is
       linear since the O(n²) fix, but a page with thousands of interactive rows feels it first.
  6. **No way to try an effect alone.**
     - An agent verifies a resolver only through a rendered page (`hozu get`) or a browser flow (`hozu browse`).
     - A person has no way to try a query or a mutation from DevTools.

## Principle check
- **Principles 8 and 9 are unchanged:**
  - eviction only drops entries that the next read recomputes;
  - a bus carries tags, not data;
  - server-fetched data is still never refetched on hydration.
- **Zero third-party runtime dependencies** for every touched package (data, runtime-server, adapter-node, cli,
  devtools): the default cache, the default bus and the HTTP bus use only web-standard APIs.
- **`scope: 'user'`** data never enters a shared cache. That stays a hard error. A replaceable data cache receives
  only public entries.
- **`hozu call` adds no new side-effect path.** It runs the same declared resolvers through the same data runtime
  as a request.

## Decision (proposed)

### A. Bounded caches with a tag index
- **`DataCache` interface:**
  - methods `get(key)`, `set(key, entry, tags)`, `deleteTags(tags) → count`, `size`;
  - option `app({ dataCache })`;
  - the default `memoryDataCache({ maxEntries: 10_000 })` is an LRU: a `Map` in access order plus a tag →
    keys index.
- **Synchronous by design:** the render path reads it inline. A shared store (Redis) is out of scope for 0.12. It
  needs an async read path and a separate ADR.
- **`memoryCache({ maxPages })`:**
  - an LRU with the same tag index;
  - `deleteTags` touches only the pages carrying a tag, not every page.
- **Eviction is invisible to correctness:** an evicted entry is recomputed by the next read, exactly as after
  an invalidation.
  - `freshness: 'static'` regions recompute on a miss instead of living forever.
  - The ISR budget already assumes a cold cache.
- **`hozu plan` reports the bounds,** and `server.stats()` returns `{ dataEntries, pages, evictions }` for
  monitoring.

### B. Cross-process invalidation bus
- **`InvalidationBus` interface:** `publish(tags)` and `subscribe(onTags) → unsubscribe`, configured as
  `app({ bus })`.
- **On a local invalidation** (a mutation, an endpoint or `server.revalidate`), the handler:
  1. drops its own pages and data;
  2. broadcasts to its live listeners;
  3. publishes.
- **On a message from the bus,** it does the same three steps without publishing again.
- **Built in:**
  - `localBus()` is the default: a no-op for one process.
  - `httpBus({ peers, secret })` is zero-dependency: it sends a signed `POST /_hozu/invalidate` to each peer
    (HMAC over the body and a timestamp, refusing replays older than 30 s) with bounded retries.
  - A Redis / NATS / Postgres `LISTEN` bus is a 20-line user module against the interface (`hozu docs deploy`
    shows one), not a dependency.
- **Delivery is at least once, and order does not matter:** dropping a tag twice is harmless.
- **Lost messages are bounded by the existing TTLs.** `'static'` public data gains an optional
  `app({ staticTtl })` safety net for multi-instance deployments (D2).

### C. `fns.js` per feature
- `fns.js` becomes `/_hozu/f/<feature>-<hash>.js`, one module per feature, holding only the `fn`s its islands
  call.
- A page modulepreloads the modules of the features its islands use.
- Module helpers are emitted once per module, not once per `fn`.
- `fn`s used only on the server (head, server render, resolvers' inputs) are not shipped.
- `hozu plan` lists each page's fn modules and their sizes.
- Budget P7 is unchanged. A new report-only metric A7 records the largest page's fn bytes for a 200-feature app.

### D. A faster `hozu check` (revised by phase 0)
Benchmark 0003 measured the 500-feature app: types 2.2 s, then validate 2.26 s, run one after the other. Loading
the source is 1.1 s of the validate time; rules and contracts are 0.23 s. TypeScript 7.0.2's `--incremental` saves
only a run with no change (0.16 s), and a one-line edit costs a full 2.0 s.
- **Parallel:** the type check runs in a child process while the Hozu checks run, so the time is the longer of
  the two, not their sum.
- **Transform cache:**
  - `@hozu/transform` keeps its output in `.hozu/transform/`, keyed by the hash of the source and the
    transform's version;
  - the CLI and `hozu serve` / `hozu dev` read it;
  - a changed file is transformed again;
  - the cache is safe to delete.
- **`tsc --incremental`** with `tsBuildInfoFile` in `.hozu/check/`, for the no-change case.
- **Dropped:** rule and contract memoisation by IR hash. The saving would be at most 0.23 s of 4.6 s, and it
  carries a correctness risk.
- **Output:** the same as today; `--json` adds `timings: { types, load, rules, contracts }`.

### E. A page payload independent of the app's size (revised by phase 0)
- Rows of a list are not separate islands any more: island runs (ADR 0023) make a 100-row list 6 islands and
  138 bytes of ids.
- **What grows is `payload.routes`:** every route of the project goes to every page with an island (9.3 KB at
  500 features).
- **The fix:** the payload lists only the routes that the page's islands can link or navigate to, and the
  generated render embeds the same subset.
- **Dropped:** the short-id work.

### F. `hozu call <feature>.<effect>`
- **The command:**
  ```
  hozu call notes.listNotes --input '{}' --session '{"user":"ada"}' --json
  hozu call notes.addNote --input '{"title":"Milk"}' --session '{"user":"ada"}' --write
  ```
- **What it does:**
  - it runs the app module in process, like `hozu get`, with the same data runtime and session store;
  - it prints the output, or the declared error with its data, and the duration;
  - for a mutation or an endpoint, it also prints the invalidated tags and, from `impact`, the queries and pages
    they refresh.
- **Where the effect runs:**
  - `runs: 'server'` uses its resolver;
  - `'either'` runs `fetch.ts` in Node with the public env;
  - `'browser'` is refused with a pointer to `hozu browse`, because it needs the visitor's browser.
- **Input checks:**
  - the input is parsed by its schema, so an invalid input prints the `Invalid` error (mutations) or the issues
    (queries);
  - `--input` may be omitted for `{}`.
- **Mutations write real data:** a resolver backed by a database writes it. `hozu call` therefore needs `--write`
  for mutations and endpoints (D4) and says so in its error.
- **Contract:** `CallOutput` in `contract.ts` and `call.schema.json`, plus a skill line in `hozu docs testing`.

### G. DevTools API panel (`hozu dev`)
- **The panel:** a new dock tab, **API**.
  - It lists the page's queries, and the mutations its machines start, with `runs`, `scope`, `freshness` and
    tags.
  - It generates an input form from each JSON Schema, prefilled from the page's current inputs.
  - Each call shows the result, a declared error or `Unexpected`, the latency and the invalidated tags.
  - Each effect links to the parts that use it (Select).
- **Where calls run:**
  - `'server'` runs through a dev endpoint `POST /_hozu/dev/call`, loopback `Host` only, like every DevTools
    endpoint;
  - `'browser'` / `'either'` run in the page through the 0.11 runner.
- **After a call:** a successful mutation re-reads the page's queries by tag, as a real mutation does.
- **Mutations are marked** "writes your development data" and need a confirm click (D5).
- **Builder and Developer modes:**
  - Builder mode shows plain names ("Load notes", "Add note");
  - Developer mode shows refs and JSON.

### H. `runs` everywhere the tools describe effects
- `inspect`, `impact` and `explain` show `runs` and where each effect is implemented (`app.ts` resolver line or
  `fetch.ts` export).
- DevTools Layers marks browser-run regions.

### I. Migration
- 0.12 is **additive** (D6).
- The 0.11 → 0.12 step rewrites nothing. It exists so the chain from 0.10 continues, and it verifies the IR as
  before.
- New defaults (cache bounds, the per-feature `fns`) change no IR and no lock.

## Options considered
1. **A shared async data cache (Redis) now.**
   - Rejected for 0.12: every read on the render path becomes async, generated render code changes, and
     streaming order is affected.
   - The bus plus bounded per-instance caches covers correctness at a fraction of the change. Revisit with
     evidence.
2. **A bus implementation per broker in the framework.** Rejected: third-party dependencies, and the interface is
   two methods. One zero-dependency HTTP bus plus a documented recipe.
3. **`fns.js` per page instead of per feature.**
   - Smaller per page, but no cache sharing between pages.
   - Per feature keeps one URL per feature across the whole site. See D3.
4. **Incremental check by file timestamps only.** Rejected: rules read the IR, not files; a changed import can
   change another feature's diagnostics. IR hashes are exact.
5. **A long-running check daemon** (`hozu check --watch`). Deferred: it needs process management, which agents
   handle poorly. The persistent cache gives most of the gain with one-shot commands.
6. **An OpenAPI export instead of `hozu call`.** Possible later. Agents need execution, not a description.

## Budgets
- **New gated budgets** (thresholds from benchmark 0003):
  - **P12 check speed:** `hozu check` after a one-line edit in the generated 500-feature app ≤ 2.6 s (today
    4.6 s). It is the median of 3, gated in `pnpm bench:scale` and reported in `pnpm bench`.
  - **P13 bounded memory:** 1,000,000 distinct public query keys through the data runtime keep at most
    `maxEntries` entries, with heap growth ≤ 64 MB (today 702 MB).
- **New report-only metrics:**
  - **A7:** the largest page's fn bytes, 200 features;
  - **A8:** the `/f0` payload at 500 features against 50, with a target within 5 % (today +71 %);
  - **P14:** bus fan-out latency over `httpBus` with 4 local peers.
- **Unchanged:** P1–P11. P7 stays ≤ 8 KiB, and P11 stays ≤ 3 KB.

## Phases
0. **Measure first.**
   - A generator `bench/scale/app.ts` writes 50 / 200 / 500-feature apps (routes, machines, contracts, `fn`s,
     lists).
   - Baselines: full check time split into types, rules and contracts; data-cache RSS per 100k keys; `fns.js`
     bytes; 100-island HTML.
   - Recorded in `docs/benchmarks/0003-scale.md`. Thresholds for P12 / P13 are set from it. **Done 2026-10-03;
     D and E are revised from its results.**
1. **Caches (A):**
   - `DataCache`, LRU `memoryDataCache` and `memoryCache({ maxPages })` with the tag index;
   - `server.stats()`;
   - budget P13.
2. **Bus (B):**
   - `InvalidationBus`, `localBus`, `httpBus`, `/_hozu/invalidate` (signed, CSRF-exempt only with a valid
     signature);
   - live fan-out from bus messages;
   - a 4-instance test inside one process (four handlers, real HTTP between them through adapter-node);
   - `hozu docs deploy`, including the Redis recipe.
3. **Client output (C, E):**
   - per-feature fn modules and `plan` output;
   - page-scoped `payload.routes` (and the same subset in generated render);
   - benchmark 0001 re-run; A7 and A8.
4. **Faster check (D):** the parallel type check, the transform cache (CLI, `hozu serve`, `hozu dev`),
   `tsc --incremental`, `--json` timings, and budget P12.
5. **Tools (F, G, H):**
   - `hozu call` (schema, contract, tests on notes and stars);
   - the DevTools API panel (browser test on `examples/studio`);
   - `runs` in `inspect` / `impact` / `explain` / Layers.
6. **Guide, migration, release:**
   - skill topics (`testing`: `hozu call`; `deploy`: caches and bus; `requests`: API panel);
   - the 0.11 → 0.12 migrate step and its test on the 0.10 and 0.11 fixtures;
   - CHANGELOG and gate.

## Measure
- **Memory:** a 1M-key run stays within `maxEntries`.
- **Bus:**
  - a mutation on one of four instances drops the tagged pages and data on all four within one bus round trip;
  - a live client on instance D receives the push.
- **fns:** a 200-feature app's largest page ships only its features' `fn`s (A7 reported). P7 is unchanged.
- **Payload:** the `/f0` payload at 500 features is within 5 % of the payload at 50 (A8), and benchmark 0001's
  interaction time is not worse.
- **Check:**
  - P12 holds;
  - output with the transform cache equals output without it on every example.
- **`hozu call`:** it returns the same result and errors as a request for each `runs`, and refuses `'browser'`.
- **API panel:** the panel calls a query and a mutation on `examples/studio`, and the page refreshes by tag.
- **Migration:** every 0.10.0 and 0.11.0 fixture migrates with an unchanged IR.

## Decisions for the owner
| # | Decision | Recommendation |
|---|---|---|
| D1 | Default bounds: `maxEntries` 10,000 data entries, `maxPages` 5,000 pages, configurable | yes |
| D2 | `httpBus` built in, plus `app({ staticTtl })` as an optional safety net for `'static'` data on many instances | yes; `staticTtl` off by default |
| D3 | `fns` split per feature (shared URL across pages) rather than per page | per feature |
| D4 | `hozu call` needs `--write` for mutations and endpoints | yes |
| D5 | The DevTools API panel may run mutations, with a confirm click and the "writes your development data" mark | yes |
| D6 | 0.12 is additive: no source rewrite, a no-op migrate step | yes |
| D7 | Phase 0 (measurement) first, and P12 / P13 thresholds set from it, before any optimisation | yes (done) |
| D8 | After phase 0: drop rule / contract memoisation and short ids; add the parallel type check, the transform cache and page-scoped routes | yes |
