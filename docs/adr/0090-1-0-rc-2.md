# ADR 0090 — 1.0.0-rc.2: a welcome page, the mark in the terminal, and the candidate's findings

**Status:** accepted · **Date:** 2026-10-13 · **Builds on:** ADR 0088 (1.0), ADR 0089 (Hozu UI)

## Context
1.0.0-rc.1 shipped. Its checks and the first Dependabot scan left two fixes (ADR 0088, candidate findings):
- `hozu add kit ui --from official` names `@hozu/variants` without a version, which installs 0.31 during the candidate;
- `@hozu/image` pinned `sharp` 0.35.4 (CVE-2026-96889).

The owner also asked for two things Nuxt and Next have:
- a first page in a new app that says what the app is and where to go next, with a favicon;
- the framework's mark printed by `npm run dev`, as Nuxt 4.6 does.

## Options

### A. The first page
| Option | For | Against |
| --- | --- | --- |
| A1. A framework component (`<NuxtWelcome>`-like) the app renders | One line in the app; updates with the package | A view the app does not own is a second way to make a page; an agent cannot change it with the rules it knows |
| **A2. The page as ordinary app source in the template** | Plain `ui.*` code the person and the agent edit or delete like any page; nothing new in the framework | It ages with the template: a new release changes only new apps |
| A3. Keep "Hello, Hozu" | Nothing to maintain | Says nothing about DevTools, `hozu check` or the agent loop |

### B. The mark in the terminal
| Option | For | Against |
| --- | --- | --- |
| B1. An image protocol (iTerm2, kitty, sixel) | Exact logo | Works in few terminals; nothing elsewhere |
| **B2. Half-block characters (▀ ▄ █) in the mark's three colours** | Works in every modern terminal; 9 lines; no dependency | A low-resolution mark |
| B3. ASCII letters | Works everywhere | Does not look like the mark |

## Decision
- **A2.** `create-hozu` writes a welcome page in `features/site/views.ts`:
  - the mark and "Your Hozu app is running";
  - four steps: ask your agent, point with DevTools, check the work (`npx hozu check`), add a page
    (`npx hozu add feature tasks --page /tasks`);
  - links to Getting started, Hozu UI and GitHub;
  - a line saying the page is ordinary source to edit or delete.

  The template also gets `assets/icon.png` as `site.icon`, so the app has a favicon from its first run. With `--ui`
  the page is built from the kit's components and colour roles only (the strict theme removes Tailwind's palette,
  trial 0029). The page has no machine, so it ships no JavaScript.
- **B2.** `hozu dev` prints the mark beside its lines:
  - the version, the local URL, the DevTools key and how to stop;
  - in colour only on a terminal (`isTTY`), not under `NO_COLOR`, `TERM=dumb` or `CI`; `FORCE_COLOR` forces it
    (`0` / `false` turn it off, `3` asks for 24-bit);
  - 24-bit colour under `COLORTERM=truecolor|24bit`, otherwise the nearest 256-colour codes;
  - without colour, the same lines without the mark.

  The mark is a text grid in `packages/cli/src/mark.ts`, generated once from `site/assets/logo.png` and quantised to
  its three colours, so the CLI keeps zero third-party runtime dependencies.
- **Findings from rc.1:**
  - `hozu add kit` names the missing packages at the installed `@hozu/core` version
    (`npm install @hozu/variants@1.0.0-rc.2`), or as the matching `file:` tarballs when the app installs Hozu from
    them;
  - `@hozu/image` uses `sharp` 0.35.5;
  - the lockfile takes `source-map-js` 1.2.2.

## Consequences
- New apps start with a page that teaches the loop; nothing changes for existing apps, and `hozu migrate` does not
  rewrite their home page.
- The dev banner is human output; `hozu dev` has no `--json`, and no tool parses its lines.
- The welcome page's steps repeat words the guide already uses, so `hozu docs` and the page do not disagree.
