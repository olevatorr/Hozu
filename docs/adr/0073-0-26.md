  (deploying should be simple), "照建議，keys 移到元素上，先寫 ADR 0073 草案".

## A. Deploying is one command
### A1. `hozu build --target <static | node | workers | vercel>`
One command writes a folder the platform takes as it is; the platform's own CLI uploads it (`wrangler deploy`,
`vercel deploy --prebuilt`, `docker build`). Hozu never talks to a platform: no account, no token, no paid API.

| Target | Writes (draft, to verify in a spike before implementation) |
|---|---|
| `static` | what `hozu export` writes today (it stays as the short form of `--target static`?) — see Q5 |
| `node` | `dist/node/`: `server.mjs` (adapter-node over the generated render, no transform at runtime), `public/`, `manifest.json`, a `package.json` with production dependencies, a `Dockerfile` (`node:22-slim`) |
| `workers` | `dist/workers/`: `worker.mjs` bundled with esbuild + `hozuTransform()` (the entry `createHandler(app, { manifest, render, env, session? })` that `examples/cart/edge.ts` writes by hand today), `assets/` (= `public/`), `wrangler.jsonc` (`main`, `assets.directory`, `compatibility_date`, and the KV binding when the app has sessions) |
| `vercel` | `.vercel/output/` (Build Output API v3): `static/` (= `public/`), `functions/index.func/` with the same web entry as Workers on the Edge runtime (`.vc-config.json` `{ runtime: 'edge', entrypoint }`), `config.json` routing the filesystem first, then the function |

- **One entry for every serverless target.** The runtime is already web-standard (no `node:*` in its import graph,
  ADR 0016; checked in a web-only vm and on Bun), so Workers and Vercel Edge share one generated entry.
- **The build and the bundle come from the same source in one run**, so the manifest fingerprints always match (today
  a person can bundle code that a different build described).
- **Q5:** keep `hozu export` as an alias of `--target static` (two forms of one thing, against principle 1), or keep
  `export` and drop `static` from `--target`. Draft: keep `hozu export` only, because a static export also verifies
  that no page needs a server; `--target` lists only server targets.

### A2. What the app needs is derived and printed
Like render modes (principle 8), deploy requirements are derived from the declarations, never configured:
- every page and effect that needs a server (the list `hozu export` prints today);
- the server env the app declares (`project({ env: { server } })`), `SESSION_SECRET` when it has sessions, the
  `remote()` URLs and secrets;
- per target: sessions on Workers and Vercel need a store shared between instances (`kvSessions` with a KV binding on
  Workers; on Vercel a KV-shaped store the person provides — no free built-in, open point); live queries need a
  long-lived connection (fine on Node and Workers, limited on Vercel's Edge runtime — to verify);
- `hozu build` without `--target` prints this table for every target, so a person or an agent sees the cheapest
  target that serves every page, and why another does not fit.

### A3. Verify what will be uploaded
`hozu browse --build dist/<target>` (and `hozu get --build`) load the produced entry (the bundled `worker.mjs`, the
Vercel function, `server.mjs`) and send requests through its `fetch`, so the steps run against the uploaded code,
not the source. A test per target builds `examples/cart` and `examples/notes`, checks the output structure and runs a
short browse script through it. Real platform deploys stay manual (Q3).

### Declined / not now
| Ask | Why |
|---|---|
| `hozu deploy` calling a platform API | An external service and credentials in the tools; the platform's CLI already does it |
| A Vercel Node (serverless) target besides Edge | Two entries for one platform; add only if Edge cannot serve a real app (e.g. live queries) |
| Netlify, Deno Deploy, Fly | Later, if asked: Netlify Functions and Deno take the same web entry; Fly runs the Docker image |

## B. A shortcut belongs to the element it presses
0.25 put `keys` on `ui.send`. The round 5 retest found its limits: no `Mod+s` to submit a form (a keydown has no form
fields, HZ027), no `/` to focus a search field, a shortcut needs a machine (the storefront hung its search shortcut
on the newsletter's machine), and a final state takes no shared `on`. They share one cause: a shortcut is "press this
control", not "send this event". **Decision:** `keys` moves to elements, and `ui.send`'s option is removed.

- **Form:** `ui.input({ name: 'q', keys: ['/'] })`, `ui.button({ type: 'submit', keys: ['Mod+s'] }, ['Save'])`,
  `ui.a({ href: ui.link(home, null), keys: ['g h'] })` is not supported (no sequences). Same grammar as 0.25 (`Mod`,
  `Ctrl`, `Meta`, `Alt`, `Shift`, `KeyboardEvent.key`), HZ014 for a bad list.
- **What a press does:** what the element's own action is. A field (`input`, `textarea`, `select`) is focused (its text
  selected); a button, link, `summary`, checkbox or radio is clicked, so a submit button submits its form (with its
  `on.submit` or natively), a link navigates, `commandfor` opens its dialog. The machine sees the same event a click
  sends, so contracts and the lock are unchanged.
- **Which element:** only elements that are rendered, visible and not disabled count; inside an open modal dialog only
  its elements count; otherwise the first in document order. Printable keys without a modifier wait while the person
  types in another field; nothing fires during IME composition (0.25 rules).
- **No machine, little JavaScript:** the browser part is a small module loaded only on pages with a `keys` element,
  island or not (it reads the attribute, not the IR). A page without shortcuts ships nothing new; P7 is unchanged (the
  0.25 matcher leaves the `extras` chunk).
- **Accessible by default:** the server writes `aria-keyshortcuts` (`Control+S Meta+S` for `Mod+s`), so screen readers
  announce it and the attribute is what the browser module reads.
- **Checks:** two elements of one view with the same key that can be visible together is HZ014 when the validator can
  tell (both outside any condition); `hozu browse` gets `press Mod+s` and reports which element it pressed.
- **Migration:** `ui.send(E, p, { keys })` is HZ014 with the fix ("put keys on the control that sends E");
  `hozu migrate 0.25 → 0.26` lists each use as a note (by hand: the right element is the author's call). 0.25 has been
  out for hours, so the cost is small.

## D. Arc blanks the window on document loads (owner's manual test)
The owner saw every navigation flash in Arc 1.167.1 (Chromium 154), query-only changes included, and nothing in
Chrome or Safari. A test without Hozu isolated it: six static variants (prerender and cross-document view transition
on or off, `html` with the page background or not) all flashed in Arc, a plain multi-page site included, and none in
Chrome or Safari. Arc blanks the window on a document load; frameworks with a client router do not show it because they
do not load documents.

| Option | Why not / why |
|---|---|
| A soft navigation (a client router) | Reverses ADR 0043 I (what a router keeps is invisible to the checker and the lock), adds a router to P7, and serves one browser in maintenance mode |
| A router only in Arc | Two navigation paths to verify for one browser; against principle 1 |
| **Document it** (owner: "選 A，文件註明就好") | **Chosen:** "How it works" says that Arc shows a blank frame on every document load and why Hozu keeps document loads |

## Risks
- Platform formats change (Build Output API, wrangler): each target has a structure test and a browse run through its
  entry; a real deploy is checked by hand before each release that changes a target.
- Vercel's Edge runtime may not hold a live stream as long as Workers or Node; if so, A2 says "live queries need node
  or workers" instead of producing a broken target.
- B is a breaking change one day after 0.25; the migrate note and HZ014 point at each use.
