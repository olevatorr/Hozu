# ADR 0088 — 1.0: a release candidate, then what 1.0 promises

- **Status:** accepted (owner, 2026-10-13: "還原度非常的高，確實有達到一個里程碑 1.0看起來沒問題了").
- **Evidence for the gate (ADR 0080):**
  - A, three roles: trial 0026 for the engineer and the non-engineer; trial 0023 arm B for the designer.
  - B, the owner's project: Mori, public site and back office (trial 0027). The owner reviewed it running
    ("還原度非常的高").
  - D, the DevTools trial: trial 0023, with trial 0028 as a regression round.
  - No open breaking change.
  - Trademark search: no mark in classes 9 or 42.
- **Not tested before 1.0:** no person outside the owner used Hozu. ADR 0080 asks this record to say so.

## Options
1. **Tag 1.0.0 now.** Nothing changed since 0.31.0, so 1.0.0 would equal it. The risk is that the release mechanics
   (a major in `hozu migrate`, versions compared across 0.x → 1.x, the scaffold's ranges) run for the first time on
   the version people take as stable.
2. **1.0.0-rc.1 under npm's `next` tag, checked, then 1.0.0 (chosen).** `npx create-hozu` keeps installing 0.31 until
   1.0.0. `npx create-hozu@next` and `hozu migrate` to the candidate exercise the major step first.
3. **A longer candidate period that waits for outside reports.** Rejected: ADR 0080 C is a bonus, not a gate, and
   waiting costs nothing only if nothing waits on it.

## Decision
- **1.0.0-rc.1:** the 0.31.0 code with version 1.0.0-rc.1.
  - It is published under the `next` dist-tag: `scripts/publish.ts` passes `--tag next` for a pre-release, so
    `latest` stays 0.31.0.
  - The GitHub release is marked pre-release.
  - `hozu migrate` 0.31 → 1.0 rewrites nothing.
- **Candidate checks:**
  - `npx create-hozu@next` from empty, then `hozu check`, `hozu get` and a container from `--target node`;
  - `hozu migrate` from 0.31.0 to the candidate;
  - Mori's public site and back office upgraded to the candidate, then `hozu check`;
  - every example and the site, with `hozu check`, `pnpm export` and `pnpm verify`;
  - trial 0023 change 9, arm B, run twice more on the candidate to see whether `shown briefly` (0.31) closes the gap
    that trial 0028 R2 left.
  A failure that needs an API change makes an rc.2; anything else is fixed in rc.2 or 1.0.0.
- **1.0.0:** the candidate with only those fixes, under `latest`. After it, `next` is moved to 1.0.0
  (`npm dist-tag add <pkg>@1.0.0 next` for each package) so `@next` never installs an old candidate.
- **A step for every minor:** `hozu migrate` keeps a 1.x app current only if each minor adds its step, so a test fails
  when the last step does not reach the CLI's own minor (from the review before the candidate).

## What 1.0 promises
From 1.0.0 on, versions follow semantic versioning over this surface:
| Covered: a breaking change waits for 2.0 | Not covered: may change in a minor |
|---|---|
| The authoring API of `@hozu/core`, `@hozu/core/component`, `@hozu/core/fetch`, `@hozu/core/preview` and the builders the guide teaches | DevTools UI, its words and its request Markdown wording |
| `app()`, `resolvers()`, `remote()`, `createHandler()` and the adapters' documented options | The human text of CLI output (`--json` is covered) |
| The IR shape that `@hozu/core/ir` exports, and the lock format | Generated render code, payload layout, client bundle internals |
| CLI commands, flags and their `--json` shapes | Performance numbers and budgets |
| What each diagnostic code means; a code may gain cases or a better fix, and is never reused | The wording of a diagnostic's message, cause and fix |
| `hozu migrate` takes an app from any 1.x to the latest 1.x without manual rewrites | Undocumented exports |

- A **new rule** that reports code which used to pass is allowed in a minor only as a warning. It becomes an error in
  the next major, unless it finds a security or correctness bug, as 0.30 A1 did.
- A **deprecation** warns for at least one minor before the next major removes it, and the CHANGELOG names it.
